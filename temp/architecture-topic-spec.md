# 架构设计主题临时 Spec

## 1. 文档状态

- 状态：Draft，供拆分方案和首批笔记评审使用
- 目标目录：`topics/architecture/`
- 主题名称：架构设计
- 内容来源：`temp/架构实战营思维导图 v0.2.xmind`、`temp/arch/*.pdf`
- 本文不是正式学习笔记，也不参与 Roadmap 生成

## 2. 背景与判断

课程材料包含 9 个模块、54 节正式课程、8 份课后作业和 1 份毕业设计，覆盖从
架构基本概念到复杂度分析、质量属性、存储/计算架构、微服务、灾备、集群以及
架构重构与演进的完整路径。XMind 适合提供课程地图，PDF 适合提供概念解释、
架构图、推导过程和案例，因此 Markdown 应以 PDF 为主要事实来源，以 XMind
校验章节关系和学习顺序。

## 3. 目标

1. 建立面向运维、SRE 和平台工程读者的架构设计学习主题，而不是完整复刻架构师课程。
2. 将课程材料提炼为可检索、可复习、可生成 Roadmap 的 Markdown 笔记。
3. 保留架构设计中的问题分析、方案备选、权衡和演进，而不是只罗列产品名词。
4. 与现有 `systems`、`cloud-native`、`data-systems`、`ai-infrastructure` 等主题
   形成互补，避免复制已有产品专题。
5. 先确定稳定的章节边界，再分批实现约 5 册正式笔记。

## 4. 非目标

- 不将 XMind 或 PDF 原文件复制到 `topics/` 作为公开学习内容。
- 不按 54 节课程机械生成文件，也不追求覆盖课程的全部理论范围。
- 不把课程讲义原文、整页截图或大段原图直接发布到公开仓库。
- 不替换现有 MySQL、Kafka、RabbitMQ、Kubernetes、GPU 等专题的产品细节。
- 不在本阶段修改根 `README.md`、`index.html` 或生成 Roadmap；这些属于正式内容
  落地阶段。
- “学习技巧”“面试晋升”等 XMind 分支不纳入架构正文，除非后续确认需要独立附录。

## 5. 运维导向的内容筛选

保留能够直接帮助运维/SRE/平台工程读者做容量规划、可靠性设计、故障隔离、
变更评审和架构演进的内容。课程中的纯架构师职业讨论、通用学习技巧、面试技巧、
与运维无关的业务案例只做背景参考，不进入正式正文。

### 5.1 建议保留

- 复杂度识别、4R、质量属性和架构图表达；
- 容量/流量估算、性能模型、缓存、负载均衡、限流、降级和熔断；
- 数据库复制、分片、分区、备份、恢复和一致性取舍；
- 高可用、FMEA、故障域、灾备、异地多活和切换演练；
- 微服务拆分、基础设施治理、集群算法和分布式协调；
- 架构重构、演进、可观测性、可测试性、可维护性和成本控制；
- 学生系统、红包、钱包、微博、消息队列、IM、秒杀等案例中的设计方法，
  但须改写为可迁移的运维问题和决策。

### 5.2 暂不纳入

- “架构师只需要写 PPT 么”等职业角色讨论；
- XMind 中的学习技巧、面试晋升和泛化的业务分析模型；
- 与运维实践没有直接关系的产品介绍或课堂口号；
- 已在现有专题中充分覆盖的产品操作细节。

首选拆成约 5 册。编号只表达推荐阅读顺序，不要求一册对应一个课程模块。

| 02 | `02-performance-and-capacity.md` | 容量估算、性能模型、缓存、负载均衡、限流与接口保护 | 模块 2、模块 4、模块 5 |

拆分可以在首批内容评审后调整为 4-6 册。若某册超过约 5,000 行，应沿自然的
知识边界继续拆分；不得为了凑册数切断一个完整的设计流程。

## 7. 正式笔记规范

每份正式 Markdown 必须：

- 以一个 H1 标题开始，且全文只有一个 H1；
- 使用 H2 表示章节，H3 表示 Roadmap 收集的学习段落，H4 表示知识点；
- 在第一个 H3 中放置章节导入，避免把说明写在 H2 与 H3 之间；
- 优先保留 Mermaid、表格、代码示例和有意义的换行；
- 对每个架构模式说明：解决的问题、复杂度来源、方案结构、关键取舍、失败模式、
  运维观察点和适用边界；
- 产品案例必须标明其是案例，不把特定厂商实践写成普遍定律；
- 使用自己的中文表述，必要时保留课程来源和讲师信息。

推荐的单章结构：

```markdown
## <章节>

### <问题与学习目标>

### <概念和复杂度模型>

### <方案与架构图>

### <权衡、风险与运维验证>

### <案例或练习>
```

## 9. 来源、版权与引用

## 10. 实施顺序

1. 先完成本 spec 的评审，确认目录名和约 5 册的边界。
2. 从 `01`、`02` 开始做小批量试写，验证运维导向、H2/H3 粒度和 Roadmap 效果。
3. 对照 PDF、XMind 和现有主题做重复内容检查。
4. 再完成存储、计算、微服务、高可用、集群和演进几个主体册次。
5. 最后补主题 `README.md`、根目录导航和 Roadmap 生成物。

## 11. 验收标准

- 每个正式 Markdown 只有一个 H1，且满足仓库的 H2/H3/H4 结构约束。
- 每个册次都有明确的学习目标、运维场景、方案权衡和适用边界。
- 课程案例、产品专题和架构通用原则之间边界清楚。
- 正式 Markdown 与生成的 `*-roadmap.html` 一一对应。
- `./scripts/build-roadmaps.sh` 成功执行，Roadmap 内嵌 JSON 有效。
- `README.md`、`index.html`、主题路径和生成文件保持同步。
- 不公开提交未经确认可发布的 PDF、XMind 原文件或受版权保护的课件截图。
- `git diff --check` 通过，且不修改与本主题无关的用户文件。

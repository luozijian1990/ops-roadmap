# DevOps 与持续交付内容整理规范

## 1. 适用范围

本规范适用于从以下目录提炼并扩展现有学习主题的内容：

- `temp/jiaofu/`
- `temp/devops/`

目标目录为现有 `topics/` 和必要的 `cases/devops/`。禁止以本批材料为理由新增 `topics/devops/` 顶层主题。

## 2. 内容分类规则

### 2.1 通用知识进入 topics

满足以下条件的内容可以进入 `topics/`：

- 不依赖某一家公司的组织名称、内部系统或不可复用的规模数字。
- 能抽象为概念、模型、流程、决策、实现方式或验证方法。
- 能与现有章节形成前后关系，而不是单独堆放课程摘要。

### 2.2 具体实践进入 cases

满足以下任一条件时，优先进入 `cases/devops/`：

- 内容围绕某家公司、团队、平台或转型项目展开。
- 关键结论依赖组织规模、历史背景、业务类型或迁移阶段。
- 材料包含可识别的实施路径、结果数据、失败原因或组织决策。

案例必须区分“原文事实”和“整理者推断”，并保留来源和核验状态。

### 2.3 暂缓内容

以下内容不进入主学习笔记：

- 开篇词、结束语、获奖名单和课程营销信息。
- 仅有复习题而没有新的知识解释的测试材料。
- 只适用于移动端或单一厂商、且无法抽象复用的细节。

这些材料可以保留在 `temp/`，作为来源索引或后续复习材料。

## 3. 归属和去重规则

1. 每个知识点必须指定一个“主归属文件”。
2. 其他文件只保留简短交叉引用，不复制整段内容。
3. 工具专题描述“怎么做”，架构和 GitOps 章节描述“为什么这样做、边界是什么”。
4. 出现重复内容时，优先保留证据更充分、结构更完整、与现有路线衔接更好的版本。
5. 同一概念在多个阶段出现时，后续章节应引用前文并增加新的深度，而不是重新定义。

推荐主归属：

| 内容 | 主归属 |
| --- | --- |
| DevOps/持续交付边界、价值流、组织采用 | `topics/delivery/gitops/01-principles-workflow-and-adoption.md` |
| CI、测试、质量门禁、Jenkins 执行模型 | `topics/delivery/jenkins/delivery-practice.md` |
| 制品、镜像、供应链、签名和证明 | `topics/delivery/gitops/02-supply-chain-security-and-operations.md` |
| Ansible 编排和主机变更 | `topics/delivery/ansible/02-playbooks-operations-and-delivery.md` |
| 平台产品、架构演进和组织规模化 | `topics/architecture/05-evolution-and-operations-cases.md` |
| 灰度、镜像自动化和 Argo CD 发布控制 | `topics/delivery/argo-cd/05-image-automation-and-progressive-delivery.md` |

## 4. 单个知识点写作模板

每个新增 H3 小节应尽量回答以下问题：

1. 这个问题或能力解决什么交付风险？
2. 它与相邻能力的边界是什么？
3. 有哪些常见方案，选择依据是什么？
4. 正常流程和失败流程分别如何运行？
5. 如何通过指标、日志、测试或演练验证？
6. 发生故障时如何停止、回滚、恢复和复盘？

建议结构：

```markdown
### 价值流瓶颈应该如何定位

先说明问题背景和适用边界。

#### 识别输入、等待和返工

解释模型，并给出表格、流程图或示例。

#### 选择改进动作

比较方案、前提、风险和退出条件。

#### 验证改进是否有效

列出指标、观察窗口、实验或回滚条件。
```

## 5. 结构要求

- 每个 Markdown 文件只能有一个 H1。
- 使用 H2 表示章节，H3 表示 Roadmap 收集的主要小节，H4 表示内部知识点。
- 章节介绍必须放在该章第一个 H3 内，不能只写在 H2 和 H3 之间。
- 保留 Mermaid、表格、代码块和有意义的 Markdown 换行。
- 单文件原则上少于 5,000 行；接近上限时沿自然章节拆分到同一 topic 目录。
- 文件名使用小写英文和 kebab-case；不要使用课程编号或中文文件名作为公开路径。

## 6. 证据和来源要求

每个重要结论至少具备一种证据：

- 官方文档或规范链接。
- 可复现的命令、配置、测试或实验结果。
- 课程 PDF 的文件名和页码/章节定位。
- 已整理案例的来源链接和核验状态。

课程材料只能作为线索，不能单独支撑强断言。遇到版本相关内容，必须注明适用版本或验证日期；遇到企业案例数字，必须标注来源、状态和是否为原文口径。

## 7. 工具和厂商内容要求

1. 先写通用模型，再写 Jenkins、GitLab、Ansible、Argo CD 等工具映射。
2. 不把某个工具的默认行为写成 DevOps 原则。
3. 工具示例应包含输入、输出、权限、失败行为和回滚方式。
4. 涉及生产配置时，避免未经验证的固定数值；应写出校准依据。
5. 已有工具专题能覆盖的内容，使用链接而不是在新章节重复完整教程。

## 8. 案例写作要求

案例文件应至少包含：

- 背景与业务约束
- 原有交付痛点
- 组织、流程和平台变化
- 技术方案与关键取舍
- 结果指标及其来源
- 风险、失败点和未解决问题
- 可迁移的通用经验
- 来源与核验状态

不能把“某企业采用了某工具”直接总结为普遍最佳实践。

## 9. Roadmap 和仓库验收

完成 Markdown 修改后必须在仓库根目录执行：

```bash
./scripts/build-roadmaps.sh
```

随后检查：

- 每个正式 Markdown 都有对应的 `*-roadmap.html`。
- 每个 Roadmap 都包含正确的 `../../../index.html` 相对回链。
- 新增或修改的 Roadmap 已被根目录 `index.html` 引用。
- `<script id="data" type="application/json">` 内容是有效 JSON。
- `topics/cloud-native/kubernetes/full-animated-roadmap.html` 及其 `roadmap-animations/` 未被覆盖。
- README 的主题和册数描述与实际文件一致。

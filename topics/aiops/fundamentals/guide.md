# AIOps 的一些理解

## 对 AIOps 的理解

### 从运维目标理解智能化
<!-- src: ../llm-aiops/00-overview.md; ../llm-aiops/01-foundations-evaluation-trust.md -->

这份笔记面向运维、SRE 和平台工程师，整理选择场景、建设能力和判断效果时值得关注的问题。内容是基于仓库已有专题的工程性提炼；文中的场景用于解释判断方法，不代表真实生产验证结果。

- AIOps 可以理解为：把统计学习、机器学习和大模型等能力用于运维任务，帮助发现异常、理解信息、辅助决策和执行处置。
- SRE 关注可靠性目标及其工程实现，AIOps 可以服务于其中的监控、排障、容量和重复劳动治理，但不替代业务目标和责任划分。
- 可观测性提供系统状态的证据，自动化负责执行明确的步骤，AI 可以参与信息理解和候选方案生成。三者需要在同一个工作流程中配合。
- 自动化程度与智能化程度应分开看：固定规则触发的自愈可能很有效，能对话的助手也可能没有任何执行权限。
- 判断是否值得引入 AI，应先写清任务输入、预期输出、使用者和错误后果，再比较它与现有方法的差异。
- 例如“让 AI 负责稳定性”范围过大；“值班人员收到告警后，自动汇总对应服务最近的变更和异常证据”更容易验证。

### 按任务选择方法
<!-- src: ../llm-aiops/01-foundations-evaluation-trust.md; ../llm-aiops/03-observability-and-signals.md -->

| 方法 | 适合承担的工作 | 需要关注的边界 |
| --- | --- | --- |
| 规则与固定工作流 | 已知阈值、告警路由、确定的操作步骤 | 规则维护和场景覆盖；属于基础能力，不必包装成 AI |
| 统计方法与机器学习 | 动态基线、异常检测、聚类、容量预测 | 数据分布、误报漏报、模型漂移 |
| LLM | 理解文本、汇总证据、检索问答、生成查询和方案草稿 | 事实错误、上下文缺失、成本与延迟 |
| LLM 驱动的 Agent | 根据中间结果选择工具，完成多步调查 | 工具权限、循环失控、执行状态与停止条件 |

- 方法可以组合，例如统计检测发现异常，规则关联服务，LLM 整理摘要，工作流执行经过授权的动作。
- 规则已经能够稳定表达的任务，应先保留为可测试的确定性逻辑，避免增加不必要的不确定性。
- Agent 是任务执行方式，是否采用它取决于过程是否需要动态选择步骤；固定查询和固定汇总也可以满足需求。
- 验证方法是否合适，要用同一批任务比较成功率、耗时和成本；模型名称、参数量和 Agent 数量不能直接证明价值。

## 场景选择

### 从明确的工作瓶颈开始
<!-- src: ../llm-aiops/01-foundations-evaluation-trust.md -->

- 先记录一线工程师反复做的事情：查哪些系统、复制哪些信息、在哪一步等待、哪些判断容易遗漏。
- 优先选择发生频率较高、输入能够获取、输出可以复核的任务，并明确实际使用者。
- 对每个候选场景记录当前人工耗时、发生次数、返工原因和错误代价，形成比较基线。
- 知识查询：关注能否找到当前环境适用的文档，以及回答是否有可靠出处。
- 告警处理：关注是否减少重复阅读，同时保留独立故障和重要告警。
- 故障排查：关注是否缩短找证据的时间，是否提供了可以继续验证的线索。
- 巡检、变更和容量规划：关注是否能识别异常与风险，以及建议是否满足业务和资源约束。
- 如果瓶颈是负责人缺失、权限申请缓慢或预案过期，应先修复对应流程；模型无法替组织补上责任和授权。
- 一个可执行的试点目标是：针对指定服务的一类告警，生成带来源的事件摘要，由值班人员复核；暂不扩大到所有服务和故障类型。

## 数据与上下文

### 让不同系统的信息能够对得上
<!-- src: ../llm-aiops/03-observability-and-signals.md; ../llm-aiops/02-ops-knowledge-and-collaboration.md -->

- 指标说明趋势，日志提供事件细节，链路帮助理解调用传播，拓扑和变更记录补充关系与时间背景。
- 汇总前先固定环境、服务、实例和时间窗口，避免把测试环境、同名服务或历史故障的数据混在一起。
- 服务标识、版本号、Trace ID 和资源归属需要能在不同系统中关联；时间戳还要考虑时区、采集延迟和时钟偏差。
- 保留查询条件、原始来源、采集时间和必要片段，使工程师能够回到原始系统复核。
- 明确区分“查询后没有发现异常”和“数据源不可用、无权限或采集缺失”。后者不能用来证明系统正常。
- 数据进入模型前，按使用者权限限制可见范围，并对凭证、个人信息和业务敏感字段做必要处理。
- 例如调查发布后错误率升高，需要对齐发布版本、异常实例、请求失败时间和下游调用；只提供一张 CPU 曲线通常无法解释完整问题。
- 验收时抽查摘要中的事实是否能回到同一环境、同一时间窗口的记录；无法复核的内容应标记为未知或推断。

## 运维知识

### 把经验整理成可以维护的知识
<!-- src: ../llm-aiops/02-ops-knowledge-and-collaboration.md -->

- 知识包括服务说明、架构依赖、SOP、Runbook、故障案例和业务限制，不能只收集操作命令。
- 每份操作知识应说明适用环境、前置条件、步骤、验证方式、失败处理和负责人。
- 文档保留版本、最近验证时间与废弃状态；历史上有效的方案不一定适用于当前版本。
- 检索增强生成（RAG）把检索到的材料提供给模型，效果仍取决于资料质量、检索范围和引用是否支持结论。
- Skills 可以组织任务方法和操作约束，MCP 可以提供工具与资源接入；两者都需要配合知识维护、权限校验和效果验证。
- 例如旧预案允许直接重启单实例服务，当前服务已经采用不同的部署和状态管理方式，就必须重新验证，不能因关键词相似直接推荐执行。
- 模型生成的复盘和预案修订先作为草稿，由负责人核对事实后再发布；未经审核的输出不应成为下一次回答的事实依据。
- 知识效果可以通过“是否检索到适用版本、引用是否正确、步骤是否可执行”抽查，而不只统计文档数量。

## 告警与诊断

### 降噪要保留业务影响
<!-- src: ../llm-aiops/02-ops-knowledge-and-collaboration.md; ../llm-aiops/03-observability-and-signals.md -->

- 告警聚合可以结合时间、服务关系、错误特征和变更背景，减少工程师重复阅读相似信息。
- 聚合结果应保留原始告警入口、影响服务、首次与最近发生时间，以及仍未恢复的对象。
- 同时发生或文本相似只能作为关联线索；两个独立故障也可能在同一时间触发。
- 异常检测需要结合周期性、业务活动和数据缺失判断。流量突然上升可能是活动，也可能是异常，需要进一步核实。
- 例如发布后出现接口失败、重试增加和下游超时，可以放进同一调查视图，但还要验证它们是否来自同一条调用链。
- 验收既看减少了多少重复通知，也看是否误合并独立事件、遗漏高影响告警或延迟了响应。
- 在聚合效果未稳定前，应保留查看原始告警和人工拆分事件的能力。

### 根因结论需要能被验证
<!-- src: ../llm-aiops/04-diagnosis-and-rca.md -->

- 区分症状、异常位置、候选原因和确认根因。“接口超时”和“数据库连接耗尽”可能仍然只是不同层次的现象。
- 对候选原因同时记录支持证据、反证、缺失信息和下一步验证方式，避免只搜集符合最初猜测的材料。
- AI 可以帮助生成查询、组织调查顺序和对比候选解释，输出必须保留证据入口及不确定性。
- 例如发布后错误率升高，先核对异常是否集中在新版本，再比较配置差异、连接状态和错误日志；时间接近本身不能确认发布是根因。
- 回滚后恢复可以支持发布相关的假设，但还需解释具体机制，排除同期流量变化或其他干预的影响。
- 证据不足时，应输出待验证项；模型自报的高置信度不能替代验证。
- 故障处理中可以先按已有预案恢复业务，根因确认在后续继续进行，不必等 AI 给出完整解释才行动。
- 一份可用的诊断结论应说明哪个对象、通过什么机制造成什么影响，以及证据和验证结果是什么。

## 工具与执行

### 把操作能力约束在明确范围内
<!-- src: ../llm-aiops/05-remediation-and-autonomy.md -->

- 查询和变更工具分别授权，并由服务端检查身份、环境、资源范围和操作权限；提示词中的约束不能代替鉴权。
- 只读查询也要限制时间范围、返回量和并发，避免高成本查询拖慢生产系统或泄露不应访问的数据。
- 变更计划应包含目标对象、当前状态、参数、预期效果、影响范围和恢复方案。
- 审批绑定具体动作和参数；环境、目标或关键参数变化后，需要重新校验授权是否仍适用。
- 执行前再次检查状态。例如批准回滚的版本已经被新的发布替换，就不能继续照旧操作。
- 为有副作用的动作设计幂等、防重、超时和重试策略。调用超时意味着结果未知，先查询实际状态，再决定能否重试。
- 日志、文档和工具返回中的文字属于待分析数据，不能因为其中写着“执行某命令”就成为新的操作授权。
- 审计记录保留谁提出、谁批准、执行了什么、结果如何，并避免让执行 Agent 修改自己的审计证据。

### 用业务恢复验证动作结果
<!-- src: ../llm-aiops/05-remediation-and-autonomy.md -->

- API 返回成功只说明请求被接受或操作完成，还需检查资源状态、服务状态和业务表现。
- 扩容后应确认新实例就绪、流量接入，以及延迟和错误率是否改善；实例数增加不能单独证明容量问题解决。
- 对示例中的发布故障，回滚后继续观察目标版本、失败请求、下游异常和核心业务成功率。
- 执行前定义观察窗口、成功条件、停止条件和失败后的处理人，避免操作后临时猜测是否恢复。
- 指标没有改善时，先重新评估假设和当前状态，不要让 Agent 连续扩大变更范围。
- 回滚也有前提。涉及数据格式或不可逆写入时，应事先验证恢复策略，不能笼统假设所有动作都能撤销。
- 如果授权到期、工具失联或实际状态未知，应停止新增变更，把已知结果和未完成事项交给负责人。

## 人机协作

### 让人能够判断并接管
<!-- src: ../llm-aiops/02-ops-knowledge-and-collaboration.md; ../llm-aiops/05-remediation-and-autonomy.md -->

- 按任务风险选择协作方式：生成草稿、人工复核、在明确授权范围内自动执行可以同时存在。
- 人工审批应看到动作对象、关键参数、证据、影响范围和恢复办法；只有一个“确认”按钮不足以支持判断。
- 高风险、不可逆或跨团队的动作，应有明确负责人决策；低风险重复任务可以在验证后逐步减少重复确认。
- AI 应区分事实、推断和建议，并展示关键工具调用及失败状态，方便工程师继续调查。
- 接管时交付事件摘要、已做动作、当前状态、剩余假设和证据链接，减少重新收集信息的成本。
- 对持续失败、证据冲突或超过时间与调用预算的调查，设置停止条件，避免无限循环。
- 例如 AI 查询不到发布记录时，应说明缺失信息并交给有权限的人核实，不能把“未查到”解释成“没有发布”。
- 验收要观察工程师是否能及时发现错误、拒绝建议并接管；采纳率高本身不能说明结论正确。

## 效果评估

### 与现有工作方式做同口径比较
<!-- src: ../llm-aiops/01-foundations-evaluation-trust.md -->

| 任务 | 应观察的结果 | 容易漏掉的代价 |
| --- | --- | --- |
| 知识问答 | 答案正确、引用适用、未知时说明缺口 | 过期文档、越权信息、核对时间 |
| 告警聚合 | 减少重复事件、保留独立故障 | 误合并、漏报、发现延迟 |
| 诊断辅助 | 候选原因质量、证据正确性、调查耗时 | 无效查询、错误引导、人工返工 |
| 受控处置 | 预期状态达成、业务恢复 | 误操作、恢复失败、额外业务影响 |

- 先记录人工、规则或已有自动化的表现，再用同类任务比较 AI 增益，避免只与“完全不处理”比较。
- 历史回放只提供当时可见的信息，避免把故障复盘里的最终答案提前放进诊断输入。
- 评测样本覆盖正常、异常、信息不足和工具失败，并隔离用于调试的案例与最终验收案例。
- 看平均耗时的同时关注尾部耗时和严重错误。诊断建议更快，但错误引导更长，也可能降低整体效率。
- MTTR 的起止口径、故障范围和复杂度需要可比，不能把同期流程改进全部归因于 AI。
- 成本包括模型调用、数据查询、存储、维护、人工审核和返工；单次 Token 费用只是其中一部分。
- 模型、提示词、知识库或工具变更后，回归关键案例，记录版本与退化情况。
- 离线通过、影子运行有效和生产收益是不同证据阶段，应分别记录，不能相互替代。

## 落地路径

### 从一个可验证的小场景逐步扩大
<!-- src: ../llm-aiops/01-foundations-evaluation-trust.md; ../llm-aiops/05-remediation-and-autonomy.md -->

1. 选择一个服务的一类重复问题，明确负责人、输入输出、当前基线和成功条件。
2. 整理所需数据和知识，确认权限、关联标识及信息缺失时的处理方式。
3. 先做只读调查或草稿生成，用历史案例核对事实、引用和失败表现。
4. 进入影子运行，与真实处理结果对照，但不让输出直接驱动生产变更。
5. 开放人工辅助使用，记录采纳、修订、拒绝和返工的原因，确认实际节省的时间。
6. 对已经验证、范围清楚且具备恢复办法的动作，建立受控执行流程和停止条件。
7. 定期复查收益、错误和维护成本，再决定扩大、保持或收缩范围。

- 这是一种试点组织方式，各阶段停留时间应由证据决定，自动执行不必成为所有场景的终点。
- 每一步都应保留原有人工入口；模型或接入服务不可用时，值班工作仍需能够继续。
- 例如先把“发布后错误率升高”的相关证据整理好，再验证诊断建议，最后才评估特定条件下的回滚执行。
- 如果多次试验仍无法获得可靠数据、效果低于基线或审核成本过高，应暂停扩展并处理具体瓶颈。

## 需要具备的能力

### 把运维基本功与 AI 工程结合起来
<!-- src: ../../reliability/sre/guide.md; ../llm-aiops/00-overview.md -->

- 业务与可靠性：理解核心链路、SLO、容量限制和恢复优先级，知道一次错误建议可能影响什么。
- 排障能力：能够使用指标、日志、链路及系统状态验证判断，发现模型解释中的缺口。
- 平台开发：能够设计 API、鉴权、工作流、状态管理和审计，把自然语言建议接到可靠的执行系统。
- 数据与知识治理：理解标识关联、时效、权限和版本管理，使输入信息可用、可查、可维护。
- 模型应用与评测：能够拆分任务、组织上下文、构建样本、分析失败，判断是否需要 RAG、Agent 或更简单的方法。
- 协作与产品意识：理解值班人员如何使用结果，设计接管和反馈流程，持续跟踪实际收益。
- 能力验收可以从一个小练习开始：拿一份脱敏故障记录，整理证据与未知项，让助手辅助分析，再独立复核结论和处置条件。
- 学习深度围绕承担的任务展开；能够解释系统为什么成功、为什么失败，比单纯接入更多工具更有帮助。

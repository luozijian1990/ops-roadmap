opOps Roadmap / 实验室返回学习路线

一个服务，六条学习路线

先跑通、再观察故障，最后用数据证明恢复。

起始应用是一份 Python 标准库 HTTP 服务，数据保存在 SQLite。它提供业务读取、存活与就绪检查、版本、结构化日志和请求计数指标。SQLite 用于降低起步门槛；MySQL / Redis 使用独立实验，不把 SQLite 恢复等同于 MySQL 时间点恢复。

准备与启动

在仓库副本中进入下列目录。基础版只需 Python 3.9+，建议预留 256 MB 内存和 100 MB 磁盘作为实验预算；这不是性能容量保证。Linux 服务管理实验另需一台可恢复的 Linux 虚拟机。Compose 数据库分支建议预留 4 GB 内存和 5 GB 磁盘，并先确认本机端口未被其他服务占用。

cd learning-paths/labs
python3 app.py
# 保持前台运行，在另一终端进入同一目录：
python3 labctl.py verify
python3 labctl.py add second-deployment
curl -fsS http://127.0.0.1:8088/api/items
curl -fsS http://127.0.0.1:8088/metrics

预期：四项检查返回 200；业务记录至少包含 first-deployment 和新增记录。日志逐请求输出状态、耗时及版本。使用 Ctrl-C 停止前台应用。重新启动会保留数据。

实验约束：应用没有用户认证，仅用于本机或隔离环境；默认监听回环地址。故障开关影响这份应用，不会修改宿主机路由、防火墙或磁盘。请使用独立状态目录，不要把真实数据放入实验。

01 / Linux：从进程到恢复

阶段起点与任务留下的证据
1. 实验环境准备可重建虚拟机、普通账号与 SSH；保存快照后启动应用。系统版本、资源、登录身份和快照恢复结果。
2. 服务管理按 安装说明部署 systemd unit；故意改错 ExecStart，再通过 journal 修复。启动失败原因、修复差异、重启后就绪结果。
3. 请求路径先用不存在的域名、未监听的端口访问，区分解析失败和拒绝连接；TLS 实验另配本地 CA。DNS → 路由 → 监听 → 应用的分层检查。证书配置步骤见 HTTPS 实验。
4. Web 与中间件运行下方 Compose 入口，发布 v2 再回退 v1；消息队列与服务发现按进阶节点选择。入口响应、版本变化和回滚后的业务验证。
5. 数据库与缓存启动 MySQL / Redis 分支，验证账号、锁等待、逻辑恢复与缓存过期；参考数据库独立实验逐步扩展。写入前后数据、拒绝访问、恢复对账与持久化边界。
6. 监控与恢复执行延迟、就绪失败与隔离恢复实验；为 /metrics 和 /readyz 接入监控及测试通知。正常 / 故障 / 恢复三组请求和告警记录。
7. 脚本与协作把 verify 接入脚本；在两台实验主机用 Ansible 执行限定任务，验证幂等和分批失败停止；让另一人复现。脚本退出码、Inventory、Playbook、变更记录和验收记录。步骤参考Ansible 专题。

命令组合先练这三项

# 在 labs 目录，先 Ctrl-C 停掉已运行的前台应用
python3 app.py > .state/app.log 2>&1
# 另一终端生成请求后，查看记录；这些命令不修改应用数据
grep '"status": 200' .state/app.log | tail -n 5
python3 labctl.py verify; echo $?
# 故障模式下再执行 verify，对比退出码；脚本中不要忽略非零状态

受控故障与恢复

python3 labctl.py fault slow
curl -s -o /dev/null -w '%{http_code} %{time_total}\n' http://127.0.0.1:8088/api/items
python3 labctl.py fault unready
curl -i http://127.0.0.1:8088/healthz
curl -i http://127.0.0.1:8088/readyz
python3 labctl.py verify
python3 labctl.py fault none
python3 labctl.py verify

预期：slow 给业务请求增加约 1 秒延迟；unready 时存活仍为 200，就绪与业务读取为 503，verify 非零退出；none 恢复为 200。这是应用模拟的依赖异常，不代表已验证真实数据库断网。

备份必须在新目录验证

python3 labctl.py backup .state/before.db
python3 labctl.py add after-backup
python3 labctl.py restore .state/before.db .state/restored/app.db
python3 app.py --state .state/restored --port 8089
# 另一终端比较原实例和恢复实例：
python3 labctl.py verify --url http://127.0.0.1:8089
curl -fsS http://127.0.0.1:8088/api/items

预期：恢复实例有备份前记录，没有 after-backup；原实例仍有新增记录。记录备份时刻、恢复耗时及数据差距。工具拒绝覆盖已存在的目标文件，重复练习请换新路径。

Compose：反向代理、版本与数据库分支

# 先停掉宿主机上占用 8088 的实验应用
docker compose up -d --build
curl -fsS http://127.0.0.1:8080/api/items
docker compose exec app python3 labctl.py --state /data add release-check
LAB_VERSION=v2 docker compose up -d app
curl -fsS http://127.0.0.1:8080/version
LAB_VERSION=v1 docker compose up -d app
# 应用重建后 Nginx DNS 缓存最多约 5 秒，暂时失败可稍后重试并保留现象
curl -fsS http://127.0.0.1:8080/api/items
docker compose --profile databases up -d mysql redis
# MySQL / Redis 的独立练习见下方说明
docker compose down

MySQL 锁等待、事务与逻辑恢复 / Redis TTL 与持久化实验 →。基础栈中的应用仍使用 SQLite；数据库分支不自动接入应用。down 保留数据卷；确认实验数据不再需要后，才使用 docker compose --profile databases down -v 删除本项目卷。

02 / 云运维：迁移同一个服务

起点：Linux 基础验收通过，具备自己的实验账号、预算和清理权限。将应用部署到私网 ECS；入口使用负载均衡，管理通道限源。第一轮保留单实例 SQLite，完成快照与隔离恢复；需要多实例共享写入时，先把应用适配到 RDS，不要把本地 SQLite 文件当作共享数据库。

顺序：账号与预算 → 私网和访问控制 → 单实例部署 → 无状态入口双实例演练 → 日志与恢复 → Terraform 重建和清理。交付资源清单、费用记录和恢复证据。此处提供迁移任务，未提供一键创建收费云资源的脚本。

03 / Kubernetes：把同一服务交给控制器

起点：容器基础与独立实验集群。使用 最小清单（单副本、emptyDir，不保留业务数据），先验证探针和资源，再自行替换 PVC。必须指定实验 context，且确认镜像已加载或推送到可访问的仓库。

docker build -t ops-roadmap-lab:local .
# 例如 kind：将镜像装入你自己的实验集群
kind load docker-image ops-roadmap-lab:local --name YOUR_LAB_CLUSTER
kubectl --context YOUR_LAB_CONTEXT apply -f kubernetes.yaml
kubectl --context YOUR_LAB_CONTEXT -n ops-roadmap-lab rollout status deploy/lab
kubectl --context YOUR_LAB_CONTEXT -n ops-roadmap-lab port-forward svc/lab 8088:8088
# 另一终端运行 verify；结束后仅清理本实验命名空间
kubectl --context YOUR_LAB_CONTEXT delete -f kubernetes.yaml

进阶顺序：故意改错探针或镜像 → 检查事件并回退 → PVC 重建数据验证 → 多节点拓扑分布与 PDB → 控制面 / Webhook 故障 → 快照恢复。emptyDir 随 Pod 删除而丢失，不能据此通过持久化验收；CSI 快照、跨节点故障域和控制面操作需要相应集群能力。交付清单差异、事件时间线和业务验证结果。

04 / DevOps：让每次发布有证据

起点：能运行测试和构建镜像。先在本地执行同一条检查，再接入自己的 CI 工具：

python3 -m unittest discover -s tests -v
docker build -t ops-roadmap-lab:local .
docker compose up -d --build
python3 labctl.py verify --url http://127.0.0.1:8080

顺序：提交与审查 → 测试门禁 → 带提交标识的镜像与摘要 → 测试环境部署 → 业务校验 → 版本回退。然后增加配置灰度、并发发布锁、凭证轮换和制品保留。模拟执行器中断后先核对实际部署状态，再重试。交付 CI 配置、构建记录、制品摘要和失败发布记录；本实验不自动安装 Jenkins 或连接外部仓库。

05 / SRE：从能响应到能衡量

起点：应用与正常业务样本。把 /api/items 的成功请求作为一个用户旅程，明确时间窗口、请求总数和延迟阈值；就绪检查不能代替用户侧 SLI。

顺序：正常样本 → slow / unready 故障 → 告警和时间线 → 恢复反证 → 备份数据对账 → 容量与持续负载。请求计数可从 /metrics 采集，耗时在结构化日志里；这份应用尚未提供 Histogram 或分布式追踪，需自行埋点后再完成相关节点。

实验设计：先写稳态假设与停止阈值，再用同一请求比较三种状态；压测明确到达率、实际完成请求和未发出请求，不能只报告并发数。最终交付 SLO、告警、复盘、数据差距与未覆盖风险。

06 / 运维开发：把手工验证变成可靠工具

起点：选择 Python 或 Go。先写清谁使用巡检、允许检查哪些目标及失败如何表达，再重写 verify 为支持 JSON 输出、超时和退出码的 CLI；随后增加任务 API、状态存储、身份授权和审计，接入有界 Worker，验证重复消息、崩溃与取消。

交付顺序：需求与实现计划 → 可测试 CLI → 带权限的任务 API → 可靠任务执行 → 受控 Agent → 监控与恢复 → 他人可安装的发布包。沿用 验收模板记录真实数据库和队列测试与替身测试的边界。

AI 协作分支：按手册的运维开发落地章节准备规格和上下文，使用成功、就绪失败、未授权目标三类固定案例评估工作流，记录失败与重试；发布关卡只用假的动作测试。基础应用未实现这些扩展，不要把无认证实验服务发布到公网。

材料范围：可运行的基础应用、Compose 配置、systemd 示例、Kubernetes 起始清单、故障及备份恢复工具。各路线的高级能力仍需按节点完成独立实验。

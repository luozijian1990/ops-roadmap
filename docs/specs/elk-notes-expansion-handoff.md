## 一、OpenSearch 实践与差异说明

### 需要回答的问题

- OpenSearch 与 OpenSearch Dashboards 分别承担哪些职责，与 Elasticsearch、Kibana 的对应关系是什么？
- 哪些日志平台原理和数据契约可以复用，哪些 API、配置、插件和 UI 需要分别维护？
- 在保留现有采集与加工链路的前提下，怎样接入 OpenSearch？

### 必须交付的内容

- 依据写作时的官方资料选定精确的 OpenSearch、Dashboards、Logstash 和输出插件版本，给出兼容依据、核查日期与未验证项。不要使用浮动 `latest`。
- 提供独立的 OpenSearch 实验配置和完整启动、初始化、写入、查询、停止步骤，明确资源需求、端口和持久化目录。
- 以 `Filebeat → Kafka → Logstash → OpenSearch → OpenSearch Dashboards` 为与原笔记衔接的完整链路；说明 Kafka 是否必需，并给出更短的入门链路选择。
- 专门核对 Filebeat 7.17 的直连边界、Logstash OpenSearch output 的版本要求、模板管理、ECS 设置、认证与 TLS。不能只修改原 Elasticsearch output 的地址。
- 对比索引与模板、Mapping 字段类型、别名、Data Stream、Ingest Pipeline、Bulk 错误处理、PIT 与分页等本书实际使用的能力。列明可复用、需改写和待验证项。
- 给出 ISM 的完整生命周期示例，包括初始化、策略绑定、滚动、保留、状态检查和失败定位，并与原 ILM 示例对应。不能把 ILM JSON 改名后当作 ISM。
- 完成 Dashboards 中的日志检索、字段筛选、聚合和看板示例；核对查询语言、Lens、Saved Objects 的差异，不承诺 Kibana 对象无损导入。
- 复核现有 `init_es.py`、`enable_ilm.py`、`export_run.py`、`probe.py` 等脚本中的版本检查、端点和响应假设，给出 OpenSearch 对应实现或明确改写清单。
- 区分自建 OpenSearch 与云托管服务，主实验采用自建路径，不能把托管服务专属功能写成通用能力。

无需执行全量历史迁移，但要说明：新建链路接入不等于已有 ES 数据、权限、策略和看板已经迁移。

## 四、索引与查询性能深入

- 解释倒排索引、分词、`text`/`keyword`、doc values、`_source` 和 segment 的作用，关联到日志的精确匹配、全文检索、排序和聚合。
- 用可重复样本展示字段设计对写入、存储和查询的影响，包括多字段、动态字段膨胀、高基数和对象结构。
- 深化 Bulk、Refresh、Flush、Merge、Translog 的取舍，说明写入吞吐、可见性、持久性和查询竞争的关系。
- 提供 Slow Log、Profile、节点/线程池指标、热点线程及相关诊断工具的使用案例，核对产品与版本差异。
- 至少给出三个“原查询 → 诊断证据 → 改写 → 结果一致性验证”的案例，覆盖大范围检索、昂贵聚合和分页/导出。
- 给出写入与查询混合负载的压测方案：样本分布、数据规模、并发、预热、缓存状态、重复次数、延迟分位数、错误率和资源观测。
- 调优前后必须保持可解释的查询语义；未经实测只提供方法和结果记录模板，不承诺固定性能提升。

## 五、冷热数据与存储成本实践

- 从日志访问频率、查询时延和保留需求推导分层策略，解释热、温、冷等概念与具体产品实现的区别。
- 分别核对 Elastic 7.17 与所选 OpenSearch 版本的分层机制、节点配置和策略；涉及插件、许可证或托管服务能力时明确条件。
- 提供一条数据从写入、滚动、转层到删除的完整实验，包含分片位置、策略状态和查询结果的观察方法。
- 解释生命周期年龄、事件时间、迟到日志和实际保留时间之间的关系。
- 深化分片规模、副本、压缩、字段索引、Force Merge、快照及独立归档的成本与恢复代价，避免把快照直接当作在线冷层。
- 在已有容量公式基础上加入节点故障余量、迁移与合并临时空间、快照存储和恢复时间约束。
- 提供同一批日志在不同 Mapping、保留与分层策略下的测量方法，并给出假设明确的成本算例；不使用无来源的云价格或虚构实测比率。

## 六、日志驱动的业务告警

- 区分平台自身监控与基于业务日志的告警，本次重点补后者。
- 至少覆盖错误率升高、特定异常突增、预期周期日志缺失三类场景，说明适用前提。
- 明确分子、分母、服务维度、最小样本量、评估周期、窗口、迟到容忍和事件时间选择，解释低流量与采集故障造成的误判。
- 解释无数据、查询失败、部分分片失败、业务恢复与采集恢复的区别。
- 为选定的 OpenSearch 告警机制给出规则、查询、触发条件、通知和恢复的完整示例；Elastic 对应方案需注明版本和功能条件。
- 说明告警分组、去重、抑制、重复通知、恢复通知与看板下钻。测试通知使用本地接收端或明确的实验渠道。
- 用正常、触发、持续、恢复、迟到和无数据样本验证规则，并明确告警后应采取的排查动作。
- 说明日志延迟、缺失与重复对统计的影响，不能把不完整日志直接视作权威业务计数。

## 七、采集与加工组件选型

- 比较 Filebeat、Fluent Bit、Vector、OpenTelemetry Collector 的定位、来源支持、解析能力、元数据、缓冲、背压、重试、可观测性和维护成本。
- 比较 Logstash、Data Prepper 与搜索后端 Ingest Pipeline 的职责和适用条件，区分采集、服务端加工与存储内处理。
- 使用固定版本的官方资料核对插件、输入输出与成熟度，不能把“理论可接入”当作“已验证完整兼容”。
- 围绕三个场景给出选型过程：存量文件日志接入、Kubernetes 容器日志、大流量且需要缓冲与复杂加工的日志链路。
- 说明何时需要 Kafka，何时较短链路已足够，并分析增加组件带来的维护和故障成本。
- 给出选择矩阵和简明决策流程，按实际需求讨论取舍，不做脱离条件的统一排名。
- 主实验继续使用已选定链路；其他组件只需提供足够说明选型的代表性配置，无需为每个组件搭建整套教程。
